أريد منك تنفيذ تعديل Frontend فقط بشكل clean وآمن جدًا، بدون أي refactor كبير، وبدون تغيير backend أو routes أو database schema.

السياق:
لدينا نظام توثيق يعمل، ويبدو أن حالة التوثيق نفسها موجودة وتم تنفيذ التوثيق بالفعل، لكن المشكلة الحالية هي أن علامات/شارات التوثيق لا تظهر في الواجهة للمستخدمين أو الإعلانات رغم أن التوثيق تم.

الهدف:
إظهار حالة التوثيق بصريًا في الواجهة الأمامية بشكل صحيح واحترافي، اعتمادًا على البيانات القادمة من backend، بدون اختراع business logic جديدة، وبدون hardcode.

المطلوب بدقة:

1) تتبع مصدر بيانات التوثيق في frontend:
- افحص responses / models / types / mappers / hooks / services المتعلقة بـ:
  - user
  - profile
  - ad / listing / property
  - verification
- حدّد الحقل الفعلي القادم من الـ backend الذي يدل على التوثيق، مثل:
  - isVerified
  - verified
  - verificationStatus
  - status
  - identityVerified
  - أي اسم فعلي موجود بالمشروع
- لا تفترض اسم الحقل، بل استخرجه من الكود الحالي والـ API models الموجودة.

2) تأكد أن بيانات التوثيق تنتقل بشكل صحيح عبر طبقات الفرونت:
- من API response
- إلى service / fetch layer
- إلى mapper / transformer إن وجد
- إلى component props
- ثم إلى UI rendering
- أصلح أي مكان تضيع فيه قيمة التوثيق أو لا يتم تمريرها.

3) أظهر شارة توثيق واضحة في الأماكن التالية فقط إن كانت البيانات متاحة هناك:
- بطاقة الإعلان
- صفحة تفاصيل الإعلان
- بطاقة/صفحة المستخدم أو المعلن
- أي مكان في الواجهة كان من المفترض أصلًا أن يظهر فيه أن المستخدم/الإعلان موثق

4) الشارة المطلوبة:
- بسيطة وواضحة واحترافية
- مثل:
  - "موثق"
  - أو "حساب موثق"
  - أو "إعلان موثق"
- مع أيقونة مناسبة إن كان المشروع يستخدم icons أصلًا
- لا تغيّر تصميم الصفحة جذريًا
- لا تضف مكتبات جديدة إلا إذا كانت مستخدمة أصلًا

5) قواعد مهمة جدًا:
- لا تعرض شارة التوثيق إلا عندما تكون الحالة مؤكدة فعلًا من البيانات
- لا تستخدم mock data
- لا تستخدم hardcoded true/false
- لا تغيّر backend
- لا تغيّر routes
- لا تكسر أي feature موجودة
- لا تنشئ verification system جديد، فقط أصلح العرض والربط الحالي

6) إن كان هناك أكثر من نوع توثيق:
- استخدم المنطق الموجود أصلًا في البيانات
- إن كانت هناك حالة مثل approved / verified / completed فاعتمد فقط الحالة النهائية المؤكدة
- تجاهل draft / pending / rejected في إظهار badge النهائي
- لكن بدون تغيير business logic خارج المطلوب

7) أريد منك أيضًا:
- إزالة أي تعارض بين أسماء الحقول في الواجهة إذا كان سبب المشكلة mismatch بين API و frontend
- توحيد القراءة داخل frontend فقط بشكل minimal patch
- مع أقل عدد ممكن من الملفات المعدلة

8) بعد التنفيذ أعطني تقريرًا مختصرًا جدًا يحتوي على:
- ما سبب المشكلة الحقيقي
- ما الملفات التي عدلتها
- ما الحقل/الحقول التي اعتمدت عليها لإظهار التوثيق
- أين أصبحت الشارة تظهر الآن

9) مهم جدًا:
قبل أي تعديل، اقرأ الكود الحالي جيدًا وحدد السبب الحقيقي أولًا.
لا تقم بتخمينات.
لا تعمل refactor شامل.
أريد minimal safe fix فقط.

10) لو وجدت أن بيانات التوثيق موجودة للمستخدم لكن غير موجودة للإعلان نفسه:
- اعرض شارة توثيق المستخدم/المعلن في الأماكن المناسبة
- ولا تخترع ربطًا وهميًا للإعلان إن لم يكن موجودًا فعلًا
- استخدم الحقيقة القادمة من البيانات فقط

ابدأ الآن بتحليل الكود ثم نفذ التعديل النهائي بشكل production-safe.
