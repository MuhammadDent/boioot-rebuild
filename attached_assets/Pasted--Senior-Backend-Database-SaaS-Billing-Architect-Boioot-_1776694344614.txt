أريدك أن تعمل الآن كخبير Senior Backend + Database + SaaS Billing Architect داخل مشروع Boioot.

🎯 المهمة الحالية:
إصلاح مشكلة pricing / public subscription data بحيث تظهر جميع الباقات للمستخدم بشكل صحيح، وخاصة الباقة المتقدمة، بدون كسر أي شيء يعمل حاليًا.

## السياق المؤكد:
- لوحة الإدارة للباقات موجودة وتعمل:
  /dashboard/admin/plans
- تم تنظيم إعدادات الباقة داخل الإدارة
- لكن في الواجهة العامة/واجهة المستخدم:
  /dashboard/subscription/plans
  لا تظهر كل الباقات بشكل صحيح

## التشخيص المؤكد:
- endpoint خاص بالتسعير العام يرجّع بيانات ناقصة أو فارغة
- يوجد احتمال قوي أن المشكلة ليست في rendering فقط
- التقرير الحالي يشير إلى:
  - /api/public/pricing لا يعرض البيانات المطلوبة
  - pricing فارغ أو ناقص
  - advanced / owner advanced لا تصل للواجهة
- صفحة plans للمستخدم قد تعرض فقط بعض الباقات وليس كلها

## المطلوب بدقة:
أريد إصلاح طبقة البيانات فقط لهذه المشكلة، وليس تحسين UX الآن.

⚠️ قيود مهمة جدًا:
- ❌ لا تغيّر UI الآن
- ❌ لا تغيّر شاشة الإدارة
- ❌ لا تعمل refactor كبير
- ❌ لا تغيّر أسماء API بدون ضرورة قصوى
- ❌ لا تكسر أي endpoint مستخدم حاليًا
- ✅ المطلوب إصلاح البيانات والربط فقط
- ✅ إذا احتجت migration أو seed أو backfill اعمله بشكل آمن
- ✅ احرص أن تبقى free/basic/advanced كلها قابلة للظهور في الواجهة العامة

# المطلوب منك خطوة بخطوة:

## 1) افحص source of truth الحقيقي للباقات
ابحث داخل المشروع عن:
- model / entity / schema الخاص بـ plans
- model / entity / schema الخاص بـ pricing أو prices أو subscription pricing
- العلاقة بين plan و price
- أي flags مثل:
  - isActive
  - isPublic
  - visible
  - published
  - enabled

حدد لي بدقة:
- من أين تأتي صفحة /dashboard/admin/plans ببياناتها؟
- من أين يأتي endpoint العام /api/public/pricing ببياناته؟
- ولماذا لا تظهر advanced للمستخدم؟

---

## 2) افحص endpoint العام المسؤول عن عرض الباقات للمستخدم
أريدك أن تحدد بالضبط:
- ما هو الملف المسؤول عن:
  /api/public/pricing
  أو أي endpoint مكافئ فعليًا
- ما هي query المستخدمة؟
- هل تعتمد على جدول pricing منفصل؟
- هل يوجد filter يستبعد advanced؟
- هل يشترط وجود price row؟
- هل يشترط publish flag؟
- هل توجد مشكلة في mapping أو serialization أو plan type filter؟

---

## 3) افحص قاعدة البيانات/الـ seed data
تحقق هل كل plan لديها pricing data صحيحة أم لا.

أريد التحقق من:
- free plan لها سعر 0 أو free tier واضح
- basic plan لها record تسعير صحيح
- advanced plan لها record تسعير صحيح
- owner advanced ليست فقط موجودة في admin UI، بل مرتبطة فعليًا بالتسعير العام

إذا كانت advanced موجودة كباقة لكن بدون pricing record:
✅ أنشئ الربط المطلوب بشكل صحيح وآمن

إذا كان هناك أكثر من جدول أو أكثر من naming convention:
✅ وحّد الربط بأقل تعديل ممكن وبدون refactor كبير

---

## 4) أصلح المشكلة بأقل تغيير ممكن
أريد Minimum Safe Fix فقط.

يعني:
- إن كانت المشكلة missing pricing rows → أنشئها
- إن كانت المشكلة filters خاطئة → صححها
- إن كانت المشكلة endpoint query ناقصة → صححها
- إن كانت المشكلة seed ناقص → أضف seed/backfill مناسب
- إن كانت المشكلة mapping بين plan tier و public pricing → أصلحها

لكن:
- لا تعيد تصميم النظام
- لا تعمل تغييرات تجميلية
- لا تغيّر structure واسع

---

## 5) المطلوب النهائي وظيفيًا
بعد الإصلاح أريد أن تكون النتيجة كالتالي:

### endpoint العام يعيد 3 باقات على الأقل:
- free
- basic
- advanced

أو ما يعادلها في naming الفعلي داخل المشروع، لكن المهم أن:
- الباقة المجانية تظهر
- الباقة الأساسية تظهر
- الباقة المتقدمة تظهر
- كل باقة معها بيانات السعر الصحيحة
- كل باقة قابلة للعرض في:
  /dashboard/subscription/plans

---

## 6) أضف verification واضح
بعد التعديل:
- شغّل فحص محلي أو عبر logs أو test بسيط
- اعرض لي النتيجة الفعلية المتوقعة من endpoint
- بيّن لي أن advanced أصبحت ترجع ضمن response
- إذا أمكن اطبع sample response مختصر

## ملاحظات تنفيذ مهمة:
- إذا احتجت تعديل بيانات موجودة، افعل ذلك بشكل idempotent قدر الإمكان
- لا تنشئ duplicated pricing rows
- لا تلمس الإدارة إلا إذا كان ذلك ضروريًا جدًا لإصلاح الربط
- إذا وجدت تسمية مختلفة عن free/basic/advanced مثل owner_free / owner_basic / owner_advanced فاحترم naming الموجود
- المهم هو إصلاح الظهور العام للمستخدم

## قبل أي تعديل:
ابدأ أولًا بقراءة وتحليل:
1. schema/models
2. endpoint العام للتسعير
3. seed/backfill إن وجد
4. صفحة المستخدم التي تستهلك endpoint

ثم نفّذ الإصلاح الصحيح، وليس تخمينات.

ابدأ الآن.
