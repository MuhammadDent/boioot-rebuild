أريدك أن تبدأ الآن بتنفيذ المرحلة التالية في مشروع **Boioot** بشكل مباشر واحترافي، مع الالتزام بـ **Clean Architecture** وعدم كسر ما يعمل حاليًا.

## سياق المشروع

* Backend: **ASP.NET Core Web API**
* Deployment: **Fly.io + Docker + GitHub Actions**
* Storage: **Cloudflare R2**
* النظام الحالي يعمل بنجاح
* رفع الصور يعمل عبر API
* الصور تُرفع إلى R2 وتُسجل في قاعدة البيانات
* يوجد ربط حالي للصور مع **Property** و **Project**
* Swagger يعمل، وAPI جاهز

## الهدف من هذه المرحلة

أريد تنفيذ تحسينات احترافية على نظام الصور تشمل:

1. **Cover Image**
2. **Sort Order**
3. **حذف الصورة فعليًا من R2 عند حذفها من قاعدة البيانات**
4. **تحسين assign-to-listing** ليصبح أوضح وأكثر مرونة باستخدام:

   * `entityType`
   * `entityId`

---

# المطلوب منك الآن

## أولًا: حلّل الكود الحالي قبل أي تعديل

ابدأ بفحص المشروع وتحديد:

* مكان كيان الصورة الحالي (`UserImage` أو ما يعادله)
* الـ controller / service / repository المرتبط برفع الصور
* طريقة حفظ بيانات الصور في قاعدة البيانات
* كيف يتم حفظ رابط R2 حاليًا
* كيف يتم تنفيذ `assign-to-listing` الآن
* هل يوجد حاليًا `PropertyId` و `ProjectId` مباشرة أم abstraction مختلف
* هل يوجد مكان مناسب لإضافة `StorageKey`, `IsCover`, `SortOrder`, `EntityType`, `EntityId`

**مهم جدًا:**
قبل تنفيذ أي تعديل، أعطني **ملخصًا دقيقًا لما وجدته في الكود الحالي** وما هي أفضل طريقة للتعديل بدون كسر النظام الموجود.

---

## ثانيًا: نفّذ التحسينات التالية

### 1) تطوير كيان الصورة

حدّث كيان الصورة ليصبح يدعم على الأقل الحقول التالية إن لم تكن موجودة:

* `StorageKey`
* `PublicUrl`
* `OriginalFileName`
* `MimeType`
* `SizeBytes`
* `EntityType`
* `EntityId`
* `SortOrder`
* `IsCover`
* `CreatedAtUtc`

إذا كان هناك تصميم حالي يعتمد على `PropertyId` و `ProjectId` مباشرة، فقيّم هل الأفضل:

* الإبقاء عليه مؤقتًا مع أقل تغيير ممكن
* أو الانتقال إلى `EntityType + EntityId`

**القاعدة:** اختر المسار الأنظف والأقل كسرًا للنظام الحالي، ثم اشرح السبب.

---

### 2) Migration آمنة

أنشئ Migration جديدة وآمنة لتحديث قاعدة البيانات بما يتوافق مع التحسينات الجديدة، مع الحرص على:

* عدم كسر البيانات الحالية
* عدم تعطيل الصور المرفوعة سابقًا
* الحفاظ على التوافق مع النظام الحالي قدر الإمكان

---

### 3) تحسين API الربط

أريد استبدال أو تطوير endpoint الحالي `assign-to-listing` ليصبح أوضح.

اقترح ونفّذ Endpoint احترافي مثل:

* `POST /api/images/attach`
  أو اسم أوضح إذا رأيت ما هو أفضل

ويكون الـ request بالشكل التالي أو ما يعادله:

```json
{
  "imageId": "GUID",
  "entityType": "property",
  "entityId": "GUID"
}
```

المطلوب:

* تنفيذ endpoint الجديد
* الحفاظ على الوضوح
* عدم الإبقاء على تسمية مضللة مثل `assign-to-listing` إذا لم تعد دقيقة

إذا احتجت إبقاء endpoint القديم مؤقتًا للتوافق، فافعل ذلك مع توضيح أنه deprecated.

---

### 4) Cover Image

أضف منطق **صورة الغلاف** بحيث:

* يكون لكل Property أو Project **صورة غلاف واحدة فقط**
* عند تعيين صورة كـ cover:

  * يتم إلغاء `IsCover` عن أي صورة أخرى لنفس الكيان
* عند حذف صورة الغلاف:

  * إذا وجدت صور أخرى مرتبطة بنفس الكيان، يتم اختيار أول صورة مرتبة كـ cover تلقائيًا
  * أو اقترح سلوكًا أفضل إن وجدت

أنشئ endpoint مناسب مثل:

* `POST /api/images/{id}/set-cover`

---

### 5) ترتيب الصور

أضف دعم **Sort Order** للصور.

أريد endpoint احترافي لإعادة ترتيب الصور دفعة واحدة، مثل:

* `POST /api/images/reorder`

بحيث يستقبل body شبيهًا بـ:

```json
{
  "entityType": "property",
  "entityId": "GUID",
  "items": [
    { "imageId": "GUID1", "sortOrder": 1 },
    { "imageId": "GUID2", "sortOrder": 2 }
  ]
}
```

المطلوب:

* التحقق أن الصور كلها مرتبطة بنفس الكيان
* تحديث الترتيب بشكل آمن
* إعادة النتيجة المرتبة

---

### 6) حذف الصورة من R2 فعليًا

هذه نقطة أساسية جدًا.

عند حذف الصورة:

* لا تكتفِ بحذف السجل من DB
* احذف الملف فعليًا من Cloudflare R2 باستخدام `StorageKey`
* إذا فشل حذف R2:

  * لا تحذف السجل من DB بصمت
  * أعد خطأ واضح
  * أو طبق سلوكًا آمنًا وفسّر اختيارك

أريد تنفيذًا نظيفًا وموثوقًا.

---

### 7) تحسين abstraction للتخزين

إذا كان التعامل مع R2 منتشرًا في أكثر من مكان، فقم بتنظيفه عبر abstraction واضح مثل:

* `IObjectStorageService`
* أو اسم مناسب

بحيث يحتوي على الأقل:

* `UploadAsync`
* `DeleteAsync`

ثم اجعل تنفيذ R2 معزولًا داخل Infrastructure.

---

### 8) الحفاظ على النظام الحالي

مهم جدًا:

* لا تكسر الـ endpoints الحالية التي يعتمد عليها النظام إلا إذا وفرت بديلًا واضحًا
* إن احتجت إعادة تسمية endpoint أو DTO، فافعل ذلك بعناية
* تجنب التعديلات العشوائية الواسعة
* اتبع أسلوب incremental refactor

---

## ثالثًا: بعد التنفيذ

بعد أن تنتهي، أريد منك أن تقدم لي ما يلي بوضوح:

1. **ملخص ما تم تعديله**
2. **أسماء الملفات التي تم تعديلها**
3. **المigrations التي تم إنشاؤها**
4. **الـ endpoints الجديدة أو المعدلة**
5. **أي breaking changes محتملة**
6. **أوامر التشغيل أو الـ migration المطلوبة**
7. **خطوات اختبار Swagger لكل endpoint**
8. **أي ملاحظات معمارية مهمة للمستقبل**

---

## رابعًا: أسلوب العمل المطلوب

* نفّذ العمل فعليًا، لا تكتفِ بالشرح النظري
* افحص الكود أولًا ثم قرر أفضل نقطة دمج
* إذا وجدت أن بنية المشروع الحالية تفرض تعديلًا مختلفًا قليلًا، اختر الأفضل هندسيًا واشرح السبب
* حافظ على التوسعة المستقبلية
* اجعل التنفيذ Production-minded
* لا تحذف شيئًا يعمل حاليًا إلا مع بديل واضح

ابدأ الآن بـ:

1. فحص الكود الحالي
2. إعطائي تقريرًا مختصرًا عما وجدته
3. ثم تنفيذ التعديلات المطلوبة خطوة بخطوة
4. ثم في النهاية أعطني ملخصًا تنفيذيًا كاملًا بكل ما تغير
