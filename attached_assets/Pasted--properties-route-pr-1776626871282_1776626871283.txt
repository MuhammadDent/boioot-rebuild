أريد تنفيذ تحسين معماري آمن جدًا لصفحة `/properties` فقط، مع الحفاظ الكامل على:

- نفس route: `/properties`
- نفس UI والتصميم 100%
- نفس الفلاتر الحالية
- نفس سلوك البحث والترتيب والتنقل
- نفس API contract
- بدون كسر أي روابط أو pagination أو query params
- بدون refactor كبير
- بدون تعديل backend أو database

🎯 الهدف:
جعل أول دفعة من العقارات في صفحة `/properties` تأتي من السيرفر (Server-first initial render)،
مع إبقاء الفلاتر والتفاعل اللاحق Client-side.

---

## المطلوب بالتحديد

### 1) لا تغيّر route إطلاقًا
يجب أن تبقى الصفحة:
`/properties`

ولا تغيّر شكل query params الحالية إن وجدت.

---

### 2) لا تغيّر التصميم إطلاقًا
أريد:
- نفس layout
- نفس grid/cards
- نفس spacing
- نفس skeleton إن كان مطلوبًا لاحقًا
- نفس الفلاتر بصريًا
- نفس الترتيب الظاهر
- نفس pagination أو load more إن وجدت

❌ لا تغيّر CSS إلا إذا كان ضروريًا جدًا
❌ لا تغيّر ترتيب العناصر في الصفحة

---

### 3) اجعل الصفحة Server-first للدفعة الأولى فقط
أريد أن:

- الصفحة نفسها (page.tsx) تجلب أول دفعة من العقارات على السيرفر
- ثم ترندر HTML جاهز بأول النتائج
- ثم يتم تمرير هذه النتائج إلى Client component كـ initial data

لكن:
- الفلاتر
- الترتيب
- تغيير query
- التفاعل اللاحق
تبقى Client-side كما هي

---

### 4) لا تغيّر الـ API الحالي
استخدم نفس مصدر البيانات الحالي الموجود للصفحة:
- نفس endpoint
- نفس response shape
- نفس mapping

❌ لا تغيّر backend
❌ لا تغيّر schema
❌ لا تغيّر أسماء الحقول

إذا احتجت فقط قراءة نفس البيانات من السيرفر بدل العميل، افعل ذلك بأقل تغيير ممكن.

---

### 5) فصل آمن بين server و client
إذا الصفحة الحالية Client-heavy، أريد تقسيمًا بسيطًا وآمنًا مثل:

- `properties/page.tsx` → Server Component
- `PropertiesPageClient.tsx` → Client Component

حيث:
- السيرفر يجلب initial results
- العميل يستقبل:
  - initialProperties
  - initialPagination/meta إن وجدت
  - initialFilters/query إن لزم

ثم يكمل نفس السلوك الحالي بدون كسر

لكن:
❌ لا تعمل refactor واسع
❌ لا تنقل منطق كثير بلا داعٍ
✅ أقل diff ممكن

---

### 6) دعم الفلاتر الحالية بدون كسر
إذا الصفحة تعتمد على search params أو filters:
- اقرأ القيم الحالية من URL على السيرفر
- واجلب النتائج الأولى بناءً عليها
- ثم مررها للعميل كحالة ابتدائية

المهم:
- لو دخل المستخدم مباشرة إلى رابط فيه filters/query params
  يجب أن يرى نفس النتائج الصحيحة من أول تحميل
- وبعد ذلك يكمل التفاعل client-side كالمعتاد

---

### 7) لا تترك الصفحة فارغة ثم تنتظر useEffect
أريد إزالة الاعتماد على:
- HTML فارغ
- ثم useEffect
- ثم API fetch
- ثم render أول النتائج

بدلًا من ذلك:
✅ أول النتائج يجب أن تظهر من السيرفر مباشرة

---

### 8) ما الذي يبقى Client-side؟
أبقِ هذه الأشياء Client-side إذا كانت موجودة:
- filter UI
- sort UI
- pagination interaction
- load more
- map toggle
- favorites buttons
- أي state تفاعلي
- أي debounced search

لكن:
❌ لا تجعل كل المحتوى الأساسي client فقط بسببها

---

### 9) الصور
إذا كان ذلك ممكنًا وآمنًا:
- لا تغيّر شكل البطاقات
- لكن إذا كانت أول صور البطاقات تستخدم `<img>` ويمكن تحويلها إلى `next/image` بدون كسر layout، اذكر ذلك فقط ولا تنفذه الآن إلا إذا كان آمنًا جدًا وبأقل تعديل
- الأولوية الآن ليست refactor الصور، بل SSR initial results

---

### 10) المطلوب قبل التنفيذ
أولًا اعرض لي باختصار شديد:

1. ما الملف الحالي المسؤول عن `/properties`
2. هل هو الآن `use client`؟
3. كيف يتم جلب النتائج الآن؟
4. ما الخطة الدقيقة بأقل تغيير ممكن؟
5. ما الملفات التي ستتغير فقط؟

ثم بعد ذلك نفّذ.

---

## المطلوب بعد التنفيذ
أعطني تقريرًا واضحًا جدًا يتضمن:

1. الملفات التي عدلتها فقط
2. ما الذي أصبح Server-side
3. ما الذي بقي Client-side
4. هل route تغيّر؟ (يجب: لا)
5. هل UI تغيّر؟ (يجب: لا)
6. هل query params ما زالت تعمل؟
7. هل الفلاتر ما زالت تعمل؟
8. هل أول نتائج تظهر مباشرة من السيرفر؟
9. هل ما زال هناك client fetch لاحق؟ ولماذا؟

---

## اختبارات إلزامية بعد التنفيذ
تحقق من التالي:

- build passes
- no TypeScript errors
- no runtime errors
- `/properties` تفتح بشكل طبيعي
- إذا فتحت `/properties` بدون filters تظهر النتائج مباشرة
- إذا فتحت `/properties` مع query params تظهر النتائج المطابقة مباشرة
- الفلاتر ما زالت تعمل
- الترتيب ما زال يعمل
- pagination/load more ما زال يعمل
- لا يوجد كسر في التصميم
- لا يوجد duplicate fetch غير ضروري عند أول تحميل إن أمكن

---

## حدود صارمة جدًا
إذا وجدت أن التنفيذ الآمن يحتاج:
- refactor كبير
- تغيير API contract
- تغيير بنية الفلاتر بشكل واسع
- تعديل backend
- تغيير تصميم

❌ لا تنفذ ذلك
✅ توقّف واشرح لي أين الخطر
✅ واقترح خيارًا أصغر وأكثر أمانًا

أريد تنفيذًا جراحيًا فقط، مثل الخطوات السابقة الناجحة.
